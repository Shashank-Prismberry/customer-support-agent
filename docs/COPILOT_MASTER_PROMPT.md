- Do not overengineer.
- Do not introduce unnecessary design patterns.
- Do not create abstractions without a real requirement.
- Do not create an independent class for every small operation.
- Do not create separate agents for quick, context and deep execution modes.

- Do not introduce additional services inside this repository.
- Avoid unnecessary dependencies.

### Preserve existing work

- Do not rewrite working modules just to follow your preferred style.
- Do not rename files or change public interfaces without explaining why.
- Do not make unrelated refactoring changes.

### Understand before implementing

Before coding a task:

1. Explain what the task is supposed to accomplish.
2. Explain the files involved.
3. Explain how the implementation fits the architecture.
4. Identify dependencies and assumptions.
5. Then implement only the requested task.

## 4. Architecture to preserve

Our architecture contains:

### Request Analyzer

Identifies:

- Execution mode: `quick`, `context`, `deep`.
- Intent: `ticket`, `knowledge`, `billing`, `general`.
- Whether conversation history is needed.
- Whether RAG is needed.
- Whether MCP is needed.
- Whether approval may be required.

The Analyzer provides planning information, not authorization.

### Supervisor

The main orchestration component.

It:

- Interprets the Analyzer output.
- Selects specialists.
- Controls execution order.
- Coordinates multi-agent workflows.
- Evaluates results.
- Handles workflow continuation and completion.
- Coordinates HITL.

Use deterministic routing for straightforward requests and LLM-driven planning for complex requests.

### Triage Agent

Handles support-ticket understanding and workflows.

It is not a catch-all for every non-billing/non-knowledge request.

### Knowledge Agent

Handles company policies, FAQs and documentation using the RAG service.

### Billing Agent

Handles invoice and refund workflows using MCP and RAG where necessary.

### MCP

Provides business operations. Do not reimplement the MCP server's business logic.

### RAG

Provides tenant- and role-filtered knowledge retrieval. Do not reimplement its vector retrieval logic.

### Backend

Owns authentication token issuance, permanent conversation history and business persistence.

### LangGraph

Owns execution state, conditional orchestration and checkpointing.

## 5. Security rules

These rules are mandatory.

- Use PyJWT.
- Pin JWT algorithm to HS256.
- Validate signature, expiry, issuer and audience.
- Read the JWT secret from environment configuration.
- Never log raw JWTs.
- Never put raw JWTs in LLM prompts.
- Never put raw JWTs in messages or checkpointed AgentState.
- Forward the bearer token to MCP and RAG in Authorization headers through request-scoped integration handling.
- Do not trust roles, customer IDs or organization IDs generated by the LLM.
- Never implement authorization decisions inside agent prompts as a substitute for backend enforcement.
- Do not bypass downstream service permissions.
- Do not expose internal notes to customers.
- Never fabricate successful ticket, invoice or refund results.

The verified user context should contain only appropriate identity claims, such as:

- `user_id`
- `customer_id`
- `org_id`
- `role`
- `email`

## 6. Integration rules

5. Ask me before assuming an external contract.

## 7. AgentState and graph design

Keep AgentState minimal and typed.

Potential fields include:

- `messages`
- `user_context`
- `execution_mode`
- `intent`
- `active_agent`
- `execution_plan`
- `conversation_context`
- `retrieved_context`
- `tool_results`
- `approval_status`

Do not add fields unless the workflow requires them.

Use LangGraph reducers appropriately.

Do not store secrets or raw bearer tokens in graph state.

Keep graph nodes focused and explicit.

Do not create a separate node for every trivial helper function.

## 8. Conversation memory

Backend owns permanent conversation history.

LangGraph checkpointing owns execution progress and interruption/resumption.

Do not treat `thread_id` checkpointing as the complete conversation-memory solution.

Use bounded relevant history rather than blindly sending the entire transcript to the LLM.

Retrieve exact business facts from backend/MCP rather than relying on an LLM summary.
